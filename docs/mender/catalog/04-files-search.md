## Answer up front: rendering libraries and their weight

- **Syntax highlighting (read-only, e.g. inside Markdown code fences):**
  **Shiki** — specifically `shiki/core` (`shiki@^4.2.0`) with the
  **JavaScript regex engine** (`shiki/engine/javascript`), NOT the WASM
  oniguruma engine. Grammars come from `@shikijs/langs/<lang>` as **per-language
  dynamic imports** (26 languages wired: bash, c, cpp, csharp, css, diff,
  dockerfile, go, html, java, javascript, json, jsx, kotlin, markdown, php,
  python, ruby, rust, sql, swift, toml, tsx, typescript, xml, yaml — plus
  aliases like `ts`→typescript, `sh`→bash, `py`→python). Nothing loads until a
  fenced code block of that language is actually rendered; a highlighter
  singleton and a bounded 200-entry LRU (`Map`, keyed by `lang\x00code`) keep
  re-renders synchronous. One shared theme, `em-syntax`, generated by
  `@emdash/theme` as CSS custom properties (`--em-syntax-*`), so light/dark
  requires **zero re-tokenization** — only a CSS class flips.
  File: `packages/ui/src/react/components/markdown/highlight.ts`.
  **Weight: light.** Core Shiki + one grammar is tens of KB; nothing is paid
  for until a language is actually used, and the whole thing is decoupled
  from Monaco (see below) — this is a separate, much smaller highlighter used
  only for *rendered* markdown, chat transcripts, etc.

- **Code editing / full-file viewing (the file tab, the diff view):**
  **Monaco Editor** — `monaco-editor@^0.55.1` (the full upstream package, not
  a stripped build) wrapped by `@monaco-editor/react@^4.7.0`. This is the
  same engine as VS Code: it ships its own TextMate-style tokenizers per
  language, a full editing/undo stack, minimap, IntelliSense-style TS/JS
  language service (configured with `noSemanticValidation: true` — only
  syntax checking, no real project type-checking), format-on-paste/type, etc.
  File: `apps/emdash-desktop/src/core/features/editor/browser/monaco/
  monaco-config.ts`. **Weight: heavy.** Monaco is multi-megabyte and pulls in
  its own web-worker-based language services; it is the single biggest UI
  dependency in this catalog's area. Rebuilding without Monaco means giving
  up: multi-cursor/full text editing in-app, the side-by-side diff editor,
  inline PR-style comments anchored to diff lines, and minimap.

- **Diagrams:** **beautiful-mermaid** (`^1.1.3`), NOT the full `mermaid`
  package. It exposes a synchronous `renderMermaidSVG(source, {colors...})`
  call that returns an SVG string directly (no async worker, no DOM
  side-effects) and is themed by passing `--em-*` CSS variable references as
  the colors, so **one cached render adapts to a theme flip with no
  re-render**. Results cached in a 100-entry LRU keyed by source text. File:
  `packages/ui/src/react/components/markdown/mermaid.ts`. **Weight: light**
  relative to `mermaid` proper (which is very heavy, has canvas/DOM
  dependencies, and is normally several hundred KB) — this is a deliberate
  lighter substitute.

- **Markdown rendering:** `react-markdown@^10.1.0` + `remark-gfm@^4` (tables,
  strikethrough, task lists) + `remark-math@^6` + `rehype-katex@^7` (LaTeX,
  via `katex@^0.16.45` — host must load `katex/dist/katex.min.css`) +
  `rehype-raw@^7` (raw HTML passthrough, `full` variant only) +
  `rehype-sanitize@^6` with a **custom sanitize schema**
  (`packages/ui/src/react/components/markdown/sanitize-schema.ts`) that runs
  *before* KaTeX so user HTML is sanitized while KaTeX's own trusted output
  passes through untouched. **Weight: moderate** — react-markdown + the
  remark/rehype plugin chain is a common, well-understood stack, not
  unusually heavy, but there are 6 plugin packages in the pipeline plus
  KaTeX's own font/CSS payload.

- **Diff rendering:** Monaco's own **diff editor**
  (`monaco.editor.IStandaloneDiffEditor`), themed via CSS-variable-derived
  Monaco color tokens (`monaco-themes.ts`) so inserted/removed line and text
  backgrounds, gutter, unchanged-region background etc. all track the app
  theme. Wrapped by a custom `StickyDiffEditor` component
  (`apps/emdash-desktop/.../monaco/sticky-diff-editor.tsx`) that also hosts
  a **comment-anchoring layer** (`monaco-comment-manager.ts`) for inline
  review comments on diff lines. There is a second, custom-built "stacked"
  multi-file diff view (`stacked-diff-view.tsx`) that stacks several files'
  Monaco diff editors in one scrollable panel with per-file
  collapse/expand, and a large-diff threshold (1,500 changed lines) used to
  decide when to warn/collapse instead of rendering everything inline.
  Image files get a dedicated **side-by-side image diff** (not Monaco) — see
  *Image diff view* below. **No separate "diff npm package"** (e.g. no
  `diff`, `jsdiff`, `react-diff-viewer`) is used for rendering — diffing is
  entirely delegated to Monaco's built-in diff algorithm; only the two
  "sides" of text are supplied by the app.

## Opening files in an external editor / app ("Open In")

### What it is
A reusable "Open In ▾" split-button + dropdown (`OpenInMenu`) that appears
wherever a workspace/file path can be opened outside the app — the project
header, file rows, etc. It is a catalog-driven integration: **29 apps** are
declared centrally with per-platform launch strategies, not a hardcoded
if/else per app.

### What the user can do
- Click the primary button to open the current path in their **preferred**
  app (persisted per-user under the `openIn.default` setting).
- Click the chevron to get a dropdown of every installed, non-hidden app for
  the current OS; picking one from the dropdown **also sets it as the new
  default** (`persistPreferredApp`).
- A bound keyboard shortcut, command id `app.openInEditor`, triggers the
  current default app without opening the menu (`openInCommandRegistry`).
- Apps the user has explicitly hidden (`openIn.hidden` setting, an array of
  app ids) are filtered out entirely.
- For a **remote (SSH) workspace**, the menu narrows to only apps that
  declare `supportsRemote: true` (and further excludes Terminal unless on
  macOS).
- On failure, a toast reports `Open in <Label> failed` with a description
  (either the backend's error string or "Application not available.").

### The 29 apps and how each is detected/launched (all in
`apps/emdash-desktop/src/core/primitives/open-in-apps/api/open-in-apps.ts`)

Detection strategy per app/platform (`checkInstalledApps`, in
`apps/emdash-desktop/src/main/core/app/service.ts`), tried in this order
until one succeeds:
1. macOS bundle id lookup (`checkMacApp`)
2. macOS app-name lookup (`checkMacAppByName`)
3. a shell "does this command exist" check (`checkCommand`, e.g. `command -v
   code`)
4. macOS `mdfind` query (used specifically to disambiguate **Android Studio
   Canary** from stable, which share one bundle id — matched by display name
   containing "Canary")
5. Windows `vswhere` (Visual Studio only)

Results are cached client-side via React Query (`useOpenInApps.ts`,
`staleTime: 5 * 60 * 1000` — 5 minutes) so the dropdown doesn't re-probe every
render.

### Launching (main process, `service.ts` `openIn()` → `openInLocal` /
`openInRemote`)
- **Local:** for apps with `openUrls` (Warp only today), tries each URL
  template via `shell.openExternal` in order until one succeeds. Otherwise
  joins `openCommands` templates with `||` (shell fallback chaining) after
  substituting `{{path}}` (shell-quoted) and `{{path_raw}}` (unquoted, for
  Windows path args), and runs it via `exec` with `cwd: target` and a custom
  external-tool environment (`buildExternalToolEnv`).
- **Remote (SSH):** editors with `supportsRemote` open via a **remote URI
  scheme** built by `buildRemoteEditorUrl` (vscode/vscodium/cursor/zed use
  the `vscode-remote://ssh-remote+...` family of URIs, opened with
  `shell.openExternal`, so the *local* app itself does an SSH-based remote
  connection). Terminal apps instead get an **actual SSH command** built via
  `buildRemoteSshCommand`/`buildRemoteTerminalExecArgs` and are launched with
  app-specific mechanics: AppleScript (`osascript`) for Terminal/iTerm2,
  direct process spawn with `-e`/`--args` flags for Ghostty/Kitty/Alacritty/
  Kaku, tried across an ordered list of launch **attempts** (bundle id open,
  app-name open, raw binary) via `launchRemoteTerminal`, which tries each in
  order and only throws if all fail.
- `openPath()` also exists as a bare "open this path with whatever the OS
  default is" (`shell.openPath`), used for e.g. opening a file with its OS
  default application rather than through the Open-In catalog. Resolves the
  real path first (`realpath`) and only works for `local` hosts.

### Settings UI
`FilesSettingsCard` (project settings) exposes **three exclusion-pattern
text areas** (see *Exclusion policy* below) but the "Open In" preference
itself (default app, hidden apps) is a separate `openIn` app-setting key
consumed directly by `OpenInMenu`/`useOpenInApps` — no dedicated settings
card was found for it in the files searched; it's set implicitly by using
the dropdown ("select and open" also persists as default).

### States
- `loading` (platform/settings/availability still resolving) — button
  disabled.
- App unavailable (`hideIfUnavailable` apps are hidden outright; others show
  disabled/greyed with a strikethrough-style unavailability, gated by
  `availability[app.id]`).
- Open failure → toast error with description.
- Remote workspace narrows the whole app list.

## The workspace file tree

### What it is
A virtualized, keyboard- and mouse-driven file/folder tree
(`packages/ui/src/react/components/file-tree/file-tree.tsx`, 900+ lines) used
as the main "Explorer" panel for a workspace. It is a dumb, fully-controlled
component (all state — expansion, selection, drafts — can be handed in by the
parent) built on a generic virtualized `TreeView` primitive shared with the
search-results tree.

### What the user can do
- **Browse**: expand/collapse folders by click (chevron area or row);
  collapsed rows can be **compacted into a single "chained" row** when a
  folder contains only one child folder recursively (`compactChains`), e.g.
  `src/app/components` rendered as one row instead of three nested ones — the
  chain's full joined name is shown, and expanding the deepest segment alone
  is enough to re-collapse the whole chain.
- **Select**: click selects; **Cmd/Ctrl-click** toggles multi-select;
  **Shift-click** selects a contiguous visual range (`selectionRange` over
  currently-visible rows only).
- **Open**: single-click on a file opens it in **preview mode**
  (`{ preview: true }` — reuses one tab, like VS Code's italic-tab preview);
  **double-click opens it pinned** (`{ preview: false }`).
- **Create**: toolbar buttons for "New file" / "New folder" (also via
  `FileTreeHandle.startDraft`) drop an inline text-input **draft row** at the
  current target directory (the selected folder, or its parent if a file is
  selected, or the target of `renderHeader`'s context) — Enter commits
  (`onCreateFile`/`onCreateDirectory`), Escape or blur-with-empty-value
  cancels.
- **Rename**: an externally-driven `renamePath` prop switches that row into
  the same draft-input UI, pre-filled with the current name; committing a
  no-op (same name) is treated as a cancel.
- **Delete / Cut / Copy / Paste / Copy path / Copy relative path / Copy
  Contents / Show in Finder** — via the row's context menu, wired up one
  level above the primitive (`editor-file-tree.tsx`), see below.
- **Collapse all / Expand all** — toolbar buttons, and imperative handle
  methods (`FileTreeHandle.collapseAll/expandAll`).
- **Drag & drop, internal**: drag one or more selected rows onto a folder to
  move them; a **500 ms hover-over-a-collapsed-folder auto-expands it**
  (`HOVER_EXPAND_MS`) so you can drag into nested folders without
  pre-expanding; a highlighted drop-target ring shows the current target; a
  `pendingMovePaths` state greys out rows mid-move.
- **Drag & drop, external-in**: dropping OS files (e.g. from Finder) onto a
  folder imports them into the workspace (`onDropExternal` →
  `importLocalFiles`).
- **Drag-out**: dragging a tree row sets a custom drag payload
  (`setDraggedWorkspaceFile`) so the file can be dropped elsewhere in the
  app, e.g. into a chat composer as an attachment reference.
- **Scroll to a path programmatically** (`FileTreeHandle.scrollToPath`,
  centers it).
- **Flat mode**: an alternate `mode: 'flat'` rendering shows all files as one
  flat, alphabetically-ish list with a secondary "directory" label per row
  instead of a nested tree — used for e.g. search/quick-open style listings.
- **Row decoration**: consumers can inject custom icons (`renderIcon`), a
  trailing decoration per row (`renderDecoration` — e.g. git-status badges),
  and per-row visual state: `muted`, `strikethrough`, and a `tone`
  (`success`/`warning`/`error`/`info`) — e.g. to show new/modified/deleted
  files differently.
- **Root-level context menu** (`getRootContextMenuItems`) for actions not
  tied to a specific row (e.g. "New File" / "New Folder" / "Paste" at the
  workspace root — confirmed present in `editor-file-tree.tsx`).
- Empty/loading/error states are built in (`Empty folder`, a spinner +
  "Loading files", or an error message with `role="alert"`-equivalent
  styling).

### File tree context menu (as wired in the actual app,
`editor-file-tree.tsx`)
`Cut`, `Copy`, `Paste`, `Copy Contents` (reads file text to clipboard, capped
at `MAX_COPY_FILE_BYTES = 10 MiB`), `Copy path`, `Copy relative path`,
`Show in Finder`/`Show in File Explorer`/`Show in File Manager` (label picked
by `detectPlatformContext().os`), `Rename`, `Delete`. Root menu additionally
offers `New File`, `New Folder`, `Paste`.

### Icons
Per-extension file icons via `resolveFileIconClass` → **devicon** CSS classes
(`devicon@^2.17.0`, e.g. `devicon-typescript-plain colored`); consumer must
load `devicon.min.css`. Symlinks get a distinct icon; directories get no
icon (chevron only).

### Back end it talks to
- **Node file-tree data**: `packages/core/src/runtimes/files/node/tree/
  tree-resource.ts` (not fully read, but wired through) plus the
  `filesWireContract.tree` **live model** (see *Files RPC contract* below) —
  keyed by `(root, sessionId, exclusions)` so two windows/panes viewing the
  same root don't share one server-side expansion state.
- **Mutations** (create/rename/move/copy/delete) go through
  `filesWireContract.fs` — see *File operations contract*.
- **Move/rename containment**: every drag-move and rename is validated
  client-side (`canMoveNode`) and, on the server, against **real-path
  containment** (`realpath-containment.ts`, `workspace-file-policy.ts`) so a
  symlink cannot be used to write outside the workspace root — see
  *Security: workspace path containment* below.
- **Exclusions**: which files are hidden from the tree is driven by the
  `treeExclude` app setting (see *Exclusion policy*).

### States
`isLoading`, `error` (rendered inline, replaces the tree body), `empty`
(root has no children and no active draft), normal, and per-row `pending`
(mid-move) / `selected` / `opened` (currently open in a tab, shown distinct
from `selected`) / custom tone states.

## Search

Two entirely separate search systems exist, both backed by the
`file-search` runtime:

### 1. Filename / "quick open" path search
- **UX**: a fuzzy-ish filename search (`searchPaths`) — SQLite-backed,
  substring/LIKE-driven server-side query (`SqliteFileSearchStore.searchPaths`,
  not full fuzzy scoring — matching happens in the store, verified the
  index/search plumbing but not a scoring function beyond what SQLite/the
  store implements). Results capped at `PATH_SEARCH_MAX_LIMIT = 200`,
  default page size `PATH_SEARCH_DEFAULT_LIMIT = 20`. Query capped at
  `FILE_SEARCH_MAX_QUERY_LENGTH = 512` chars.
- **Indexing model**: each workspace root is **registered/leased** with a
  refcount (`createFileSearchRuntime` in `apps/emdash-desktop/src/main/core/
  file-search/runtime-client.ts`) — multiple UI consumers (tree, search box,
  quick-open) share one underlying index build per root; the index is
  released (and can be **evicted**, dropping the on-disk data) once nobody
  holds interest. Index state machine per root:
  `starting → active{ availability: building|searchable|failed,
  watcher: attaching|live|degraded } → failed`. So the UI can show "index
  still building" distinct from "no results" distinct from "watcher lost
  live updates, results may be stale".
- **Storage**: a **separate SQLite database file** from the app's main DB
  (`resolveFileSearchDatabasePath` → `<app-db-name>-file-search.db`), written
  via `better-sqlite3` + `drizzle-orm`, with **generation-numbered rebuilds**
  (`beginBuild` deletes rows from the *previous* generation, allowing an
  in-progress rebuild to run alongside the still-queryable old generation).
- **Exclusions** for this index come from the `searchExclude` app setting,
  applied via a revisioned reconciliation loop so a settings change
  re-indexes affected roots without racing in-flight builds.
- File used for the actual RPC call from the renderer/desktop side:
  `apps/emdash-desktop/src/main/core/file-search/runtime-client.ts`
  (`searchFileSearchRoot`).

### 2. Content ("find in files") search
- **UX**: results render in `SearchResultsTree`
  (`packages/ui/src/react/components/search-results-tree/`) — a
  file-grouped, collapsible virtualized tree. Each file row shows name,
  parent directory, and a match-count badge; expanding it reveals one row
  per matching **line**, with the line number and a **highlighted preview**
  (`highlightSegments`, `<mark>` around each matched range). Rows are
  keyboard-navigable with **ArrowUp/ArrowDown** jumping between all result
  rows (both file headers and match rows) via `data-search-result` markers.
  Click a match = open preview (`{preview:true}`); double-click = open
  pinned (`{preview:false}`).
- **Search-as-you-type**: driven from `apps/emdash-desktop/src/core/features/
  editor/browser/task-editor/file-content-search.tsx` — **200 ms debounce**
  (`SEARCH_DEBOUNCE_MS`), executed as a **cancellable streaming "live job"**
  (`createLiveJobReplicaCache` over `searchContract.searchWorkspaceContent`)
  with **progressive results** (`job.onProgress`) merged/deduped as they
  arrive (`mergeContentSearchFiles`) rather than waiting for completion —
  results can appear and grow while ripgrep is still running, and the search
  is `cancel()`-able (e.g. on a new keystroke or unmount).
- **Search engine**: an actual `rg` (**ripgrep**) subprocess
  (`packages/core/src/runtimes/file-search/node/content/ripgrep/
  ripgrep-content-searcher.ts`), invoked with `--hidden --no-require-git
  --no-config --json --fixed-strings --ignore-case --no-follow` plus
  per-exclusion `--glob`/`--iglob` flags. **Notably: search is always literal
  substring + case-insensitive at this layer** — `--fixed-strings` is
  hardcoded, so there is no regex-search toggle exposed through this path (at
  least not in the args builder read). Output is streamed **NDJSON**, parsed
  incrementally by a custom line-framer (`RipgrepJsonFramer`, guards against
  a pathologically large single JSON record via `maxRecordBytes`, default
  32 MiB) rather than buffering the whole process output.
- **Limits**: `CONTENT_SEARCH_MAX_LIMIT = 10,000` matches,
  `CONTENT_SEARCH_DEFAULT_LIMIT = 1,000`; a single line's preview text is
  capped at `CONTENT_SEARCH_MAX_PREVIEW_LENGTH = 16,384` chars; a query
  cannot contain a NUL or newline (search is line-oriented).
- **`under`** (optional) scopes a content search to a subdirectory of the
  root.

### Shared back end
Both search kinds share exclusion handling
(`normalizeExclusionPatterns`/`DefaultFileSearchExclusions`) and the same
per-root lease/availability model. Errors are typed and distinguished as
*transient* (`index-not-ready`, `root-not-registered` — logged quietly,
UI should just show "still indexing") vs. real failures.

## File operations (the "files" RPC contract)

`apps/emdash-desktop/src/core/features/files/api/contract.ts` defines the
full surface the UI can call for a workspace's files, all keyed by a
`ResourceUri` (a serialized host+absolute-path reference — host resolution
happens client-side so a `workspaceId` never has to cross the wire):

- `fs.exists`, `fs.realPath`
- `fs.readText` (with options), `fs.readBytes` — a **download-style**
  streamed procedure (not a plain call) capped at `MAX_FILE_UPLOAD_BYTES`
  for uploads and presumably similar for reads
- `fs.upload` — an **upload-style** streamed procedure, with an `overwrite`
  flag
- `fs.createFile`, `fs.createDirectory`
- `fs.rename`, `fs.move`, `fs.copy` (all take `{from, to}` as two
  `ResourceUri`s, same host)
- `fs.delete` (with an optional `recursive` flag)
- `tree` — a **live model** (server pushes updates, not just responds to
  polls) keyed by `(root, sessionId, exclusions)`
- `content` — a **live model** keyed by `(uri, source)` where `source` is
  either `'disk'` (writable, live-watched, i.e. edits + external changes
  both flow through it) or `{ ref: <git ref> }` (a **read-only snapshot** of
  that file at a specific git ref/diff-mode — this is what powers the diff
  viewer's "before" and "after" sides without a separate file-read path)

This dual-source `content` model (disk vs. git-ref) is the architectural
seam that lets the same "open file" machinery serve both the live editor tab
and every diff view.

### The open-file store (editor tab lifecycle)
`apps/emdash-desktop/src/core/features/editor/api/browser/open-file-store/
open-file-store.ts` (1,000+ lines) manages every open file's live content
lease. Notable, concretely observed behavior:
- `ContentStatus`: `loading | ready | orphaned | error(code)` — `orphaned`
  specifically means the file was deleted out from under an open tab.
- `FIRST_LOAD_DEADLINE_MS = 10,000` — if no content state arrives within 10s
  of opening, the tab classifies itself as an unavailable-error placeholder
  rather than spinning forever.
- `OPEN_FILE_LINGER_MS = 15,000` — after the last consumer releases interest
  in a file, its live subscription is kept warm for 15s before actually
  tearing down (so flipping quickly between recently-closed tabs doesn't
  re-fetch).
- `BUFFER_AUTOSAVE_DEBOUNCE_MS = 2,000` — dirty buffer text is
  crash-recovery-autosaved 2s after the user stops typing.
- `SaveFileError`: `not-open | readonly | no-etag | conflict | write-failed`
  — **etag-based optimistic concurrency**: saving requires the etag the
  content was last read at; a mismatch surfaces as `conflict` (someone/
  something else changed the file since it was loaded), distinct from a
  generic write failure.
- Dirty/conflicted/saving flags are all exposed per open file for tab UI
  (unsaved-dot, conflict indicator, spinner).

## Viewing a file (renderer routing)

`apps/emdash-desktop/src/core/features/editor/browser/renderers/types.ts`
defines the full set of file "kinds" the app knows how to show:
`text | csv | markdown | html | svg | image | too-large | binary`.

- **text** → Monaco standalone editor (full edit capability; language chosen
  by extension/Monarch grammar built into Monaco).
- **csv** → `csv-renderer.tsx`: parses and renders as an HTML `<table>` with
  a sticky header row, alternating row shading, and **hard preview caps**:
  `MAX_PREVIEW_ROWS = 1000`, `MAX_PREVIEW_COLUMNS = 100` (`csv-parser.ts`);
  a footer note appears when rows/columns were truncated. Source/rendered
  toggle lives in a container above this component (not itself in this
  file).
- **markdown** (`.md`/`.mdx`) → the shared `Markdown` component (see
  *Markdown rendering* below) with a resolver for local/relative images
  (reads bytes from disk and turns them into a `data:` URI, or shows an
  inline "Image not found" placeholder) and a link-open interceptor that
  routes relative links to opening another workspace file (in a new
  preview/pane) rather than the OS browser.
- **html** → a dedicated `HtmlContentRenderer` (path found but internals not
  read in depth here — routes raw HTML content for preview).
- **svg** → rendered as an `<img>` via a `data:image/svg+xml` URI
  (i.e. **not parsed/sanitized as markup**, just displayed as an image),
  wrapped in the same `ExpandableImage`/zoom-dialog component images use.
- **image** (png/jpg/gif/webp/ico/bmp) → `ImageRenderer`, also
  `ExpandableImage`.
- **too-large** → a distinct kind (not read in depth, but the type exists
  separately from `binary`, implying a size-based cutoff before content is
  even fetched for preview).
- **binary** → "Binary file — no diff available" / equivalent fallback
  message rather than any preview attempt.

Every text-capable renderer shares one Monaco option set
(`DEFAULT_EDITOR_OPTIONS` in `renderers/utils.ts`): minimap on, 13px font,
line numbers on, **word wrap on**, `renderWhitespace: 'selection'`, smooth
cursor + smooth scrolling, and **format-on-paste and format-on-type both
on** (i.e. Monaco will reformat code as you type/paste, using its built-in
language formatters).

## Diff viewing

### Text diffs
`StickyDiffEditor` (`apps/emdash-desktop/src/core/features/editor/
contributions/browser/monaco/sticky-diff-editor.tsx`) wraps Monaco's diff
editor. It is fed two "sides" (`original`/`modified`) resolved via
`useDiffFacets`, each side being either **disk content** or a **git-ref
snapshot** (staged / a commit / a PR base or head / HEAD), so the same diff
UI handles: unstaged changes, staged changes, a specific commit, and a PR's
file list.
- **Inline review comments**: `useDiffEditorComments` +
  `monaco-comment-manager.ts` anchor a comment thread widget to a specific
  diff line, keyed by a `DraftCommentTarget` discriminated by context
  (`working-tree` / `pr` / `commit`, each carrying enough identity — path +
  the relevant SHAs/oids — to survive being reopened later). Add / edit /
  delete comment actions all round-trip through a `draftComments` store.
- **Preview mode for text diffs**: when the file is markdown or HTML, a
  toolbar toggle switches from the raw Monaco diff to a **rendered preview
  of the modified side only** (`DiffContentPreview`) — for markdown this is
  the same `Markdown` component used elsewhere, with the same
  image-resolution and link-interception behavior, scoped to the file's
  containing directory so relative links/images resolve correctly.
- **Deleted files**: explicit "Deleted file — no preview available" state
  when previewing a deleted file's diff.
- **Status overlay** while a side is loading/erroring: distinguishes
  `too-large` ("File too large to display in the editor"), `orphaned`
  ("File was deleted on disk"), and a generic "Could not load file".

### Stacked (multi-file) diff view
`stacked-diff-view.tsx`: renders several files' Monaco diff editors stacked
in one scrollable panel, each with a collapsible header showing a formatted
`+X −Y` line-count summary (`formatDiffLineCount`) and file icon; a
**1,500-line change threshold** (`LARGE_DIFF_LINE_THRESHOLD`) gates some
different treatment for very large diffs (INFERRED to be auto-collapse or a
"large diff" warning, based on naming — not fully traced).

### Image diffs
`image-diff-view.tsx`: a dedicated (non-Monaco) side-by-side viewer for
image files that changed. Loads "original" and "modified" bytes
independently — original from a git source (`head | index | revision(sha)`)
or, for the unstaged case, from disk — and classifies each side into
`loading | ready(dataUrl, mimeType, size) | missing | unavailable(reason) |
error(message)`, where `reason` distinguishes **too-large**, **lfs-pointer**
(the file is a Git-LFS pointer that was never smudged/downloaded — shown as
"Preview unavailable — Git LFS smudge filter not applied") and generic
`git-error`. File sizes are formatted for display (`formatBytes`).

### Binary diffs
Plain "Binary file — no diff available" message, no attempt at a preview.

## Diagrams (Mermaid)

Two related but distinct UI surfaces:
1. **Inline in markdown**: a ```` ```mermaid ```` fenced code block renders
   via `MermaidBlock` — a small inline SVG preview (click, or **Enter/Space
   for keyboard users**, to expand) plus a hover-revealed expand button, and
   a full pan/zoom dialog (`ZoomViewerDialog`, shared with the image viewer —
   see below) for a closer look. Render failures show a generic "Unable to
   render Mermaid diagram." message plus the raw source in a `<pre>` block
   (with the specific error message appended only if it differs from the
   generic text) rather than crashing the page.
2. **Standalone dialog**: `MermaidViewerDialog`
   (`packages/ui/src/react/components/mermaid-viewer/index.tsx`) — a
   simpler modal that takes a **pre-rendered SVG string** (not raw source)
   and a title; used where the SVG has already been produced elsewhere (e.g.
   an agent-generated diagram surfaced outside a markdown context). Shows
   "Couldn't render diagram." if `svg` is `null`.

Rendering itself is synchronous (`renderMermaid`/`renderMermaidSVG`, see
*Answer up front*) and cached (100-entry LRU) — no loading spinner state is
needed for the render step itself, only for whatever fetches the source.

## Image viewing

`packages/ui/src/react/components/image-viewer/`:
- **`ContainedImage`** — the base `<img>` primitive, `object-fit: contain`
  letterboxing.
- **`ExpandableImage`** — wraps any inline image (in markdown, SVG preview,
  file renderer) with a hover-revealed "expand" icon button; the pan/zoom
  dialog is **mounted lazily on first open and then kept mounted** (an
  `hasBeenOpenedRef`) so reopening the same image is instant thereafter.
- **`ImageViewerDialog`** — a standalone dialog variant that takes a
  `src`/`alt` pair directly (used when there's no inline image element to
  wrap, e.g. opening an image file from the tree/tab); shows "Image content
  unavailable." if no `src` resolved.
- **`ZoomViewerDialog`** — the shared pan/zoom chassis (used by images,
  Mermaid diagrams, and generically any SVG/markup) built on
  `react-zoom-pan-pinch@^4.0.3`. Behavior, precisely:
  - Auto-**fits content to the viewport** on open (`fitContentToView`,
    scheduled a frame after layout via `requestAnimationFrame`), clamped
    between `MIN_ZOOM = 0.5` and `MAX_INITIAL_ZOOM = 12`.
  - **Dynamic zoom bounds derived from the fit scale**
    (`zoomBoundsForFitScale`): min = `max(0.5, fitScale * 0.5)`, max =
    `min(64, max(fitScale * 10, fitScale + 4))` — so a tiny icon and a huge
    diagram both get sensible, size-appropriate zoom ranges instead of one
    fixed range for everything.
  - Toolbar: **zoom in** (+0.25 step), **zoom out** (−0.25 step), **fit to
    view** (animated, 200 ms), **close**. Mouse wheel zoom step is a finer
    0.12. **Double-click toggles** zoom (`doubleClick: { mode: 'toggle' }`).
  - The transform **resets whenever `contentKey` changes** (keyed remount of
    `TransformWrapper`) — so navigating to a different image/diagram inside
    an already-open viewer starts from a fresh fit rather than carrying over
    the previous zoom/pan.
  - Render-prop children form (`children` can be a function receiving
    `{fitToView}`) lets async content (e.g. an image `onLoad`) trigger a
    re-fit once its real dimensions are known.

## File watching (live UI updates)

### What it is
A shared, deduplicated, cross-process file-watching service
(`packages/core/src/services/fs-watch/`) that is the reason the file tree,
diff views, and open editor tabs update live when something changes files
on disk — whether that's the user editing outside the app, a git checkout,
or **an agent** (the app's core use case) editing files.

### How it works
- **Contract**: `fsWatchContract` (a `resourcedStream` RPC) — consumers
  subscribe to a `{root, ignore[]}` key and receive a stream of either
  `{kind:'events', events:[{kind:'create'|'update'|'delete', path}]}`
  batches or `{kind:'resync'}` signals.
- **Deduplication**: `createWatchService` keys a shared channel by
  `(realpath(root), sorted(ignore))` — **two consumers watching the same
  root with the same ignore set share exactly one native watcher**;
  different ignore sets create separate subscriptions (this is explicitly
  documented as a design constraint: "consumers watching the same root
  should agree on the ignore set").
- **Per-consumer debounce**: `watch()` takes an optional `debounceMs` and
  coalesces bursts of events into single batched callbacks per consumer
  (not shared — each consumer can debounce independently even on a shared
  channel).
- **Native backend (local)**: `@parcel/watcher@^2.5.6`
  (`native-watch.ts`) — one native subscription per `(root, ignore)`. Handles:
  - **Gap recovery**: `@parcel/watcher` can report an FSEvents "dropped
    events" condition (`isDroppedEventsError` regex-matched against the
    error); on detection the watcher **resubscribes and fires `resync`** so
    every consumer knows to treat derived state as stale and refetch rather
    than trust incremental deltas.
  - **Resubscribe backoff**: `RESUBSCRIBE_DELAY_MS = 250`, capped at
    `MAX_RESUBSCRIBE_DELAY_MS = 30,000` (30s) — an exponential-ish backoff
    rather than hammering a broken watch.
  - `RESYNC_DELAY_MS = 250` debounces resync signaling itself.
- **Process/remote backend**: `process-backend.ts` — same contract but
  proxied to a **remote host's own watch RPC** (over the `ContractClient`
  wire), with `onReattach` also firing a resync — this is what makes file
  watching work for **SSH-remote workspaces** through the same UI code path
  as local ones.
- **Ignore-glob layering**: `profiles.ts` composes the final ignore list from
  a small hardcoded structural rule (`.git/**` for a working-tree watch,
  `objects/**`/`subtree-cache/**` for a Git-metadata-only watch) plus the
  **user-configurable `watcherExclude` app setting**, which *replaces* (not
  merges with) the built-in default list of dependency/build directories
  when the user sets it.

### Exclusion policy (shared engine behind tree/search/watch exclusions)
`packages/core/src/primitives/exclusion-policy/api/exclusion-policy.ts` — one
class, three consumers (tree, search, watcher), each getting its own default
pattern list:
- `DEFAULT_SEARCH_EXCLUDE`: 40+ entries incl. `.git`, `node_modules`, `dist`,
  `build`, `.next`, `.cache`, `__pycache__`, `venv`/`.venv`, `target`,
  `.terraform`, and — notably — **every AI coding tool's own dotfolder**:
  `.conductor`, `.cursor`, `.claude`, `.devin`, `.amp`, `.codex`, `.aider`,
  `.continue`, `.cody`, `.windsurf`, plus `.emdash` itself and
  `worktrees`/`.worktrees`/`.checkouts`/`checkouts`.
- `DEFAULT_TREE_EXCLUDE`: minimal — just `.git`, `.DS_Store`, `Thumbs.db`
  (the tree is meant to show almost everything by default).
- `DEFAULT_WATCHER_EXCLUDE`: glob-form, targeted at the highest-churn/most
  expensive-to-watch paths: `**/.git/objects/**`, `**/.git/subtree-cache/**`,
  `**/node_modules/**`, `**/.hg/store/**`.
- Pattern matching: a **bare segment** (no `/`, no glob metacharacters, e.g.
  `node_modules`) matches that literal path segment anywhere in the tree
  (cheap `Set` lookup); anything else is compiled as a real
  `minimatch@^10.2.5` glob and matched against the path and **every one of
  its ancestor paths** (so `foo/**` excludes not just descendants but the
  directory itself and all parents up to root, needed for both ripgrep-glob
  and watch-ignore-glob generation, which need slightly different glob
  shapes — `ripgrepGlobs()` emits negative `!` globs, `watchIgnoreGlobs()`
  emits positive ones for both the segment and its `/**` descendant form).
- **Case sensitivity**: defaults to case-sensitive everywhere except
  Windows (`process.platform !== 'win32'`), explicitly guarded so it's safe
  to import this module in a renderer context where `process` may not exist.

### Settings UI (`FilesSettingsCard.tsx`)
Three plain multi-line **textareas**, one pattern per line, each with its
own title/description and an individual "reset to defaults" button that only
appears when the field has been overridden from default
(`isFieldOverridden`). Patterns are normalized (trimmed, de-duped,
backslash→forward-slash, trailing-slash-stripped, `./`-prefix-stripped) on
blur-commit, not on every keystroke. The **watcher exclusions** field
carries an explicit user-facing warning: *"Watching dependency or build
folders can use tens of thousands of native watches. Changes apply after
restart."*

## Disk usage measurement

`packages/core/src/services/fs-usage/node/index.ts`
(`measureAbsolutePathUsage`) — a recursive, from-scratch directory walker
(not `du`) that computes, per path:
- `apparentBytes` (logical file size sum)
- `diskBytes` (actual disk blocks × 512, i.e. real allocation including
  block-size rounding)
- `exclusiveDiskBytes` (disk bytes **excluding hard-linked content shared
  with something outside the scanned tree** — correctly counts a
  multiply-linked file's space only once per link group found inside the
  scan, and zero if the file has links `> count found`, implying it's
  shared outside)
- `artifactBytes` — bytes attributable to specific "artifact root" relative
  paths passed in
- per-path `errors[]` (stat/readdir failures collected, not thrown, so a
  permission error on one subdirectory doesn't abort the whole measurement)

**Consumer**: `measureWorkspaceUsage`
(`packages/core/src/runtimes/workspace-registry/node/measure-usage.ts`) —
used to show a workspace/worktree's real disk footprint, specifically
splitting out **"reclaimable" space**: it runs `git clean -ndX --` (dry-run,
git-ignored-only clean) to get the list of build-artifact roots, verifies
each resolved path is actually contained within the workspace (defense
against a malicious/weird `.gitignore` reporting something outside the repo
— returns an explicit `unsafe-artifact-path` error if not), and reports
`{ totalBytes: exclusiveDiskBytes, artifactBytes }` — i.e. "this workspace
uses X total, of which Y is regenerable build output you could delete."
INFERRED UI: shown when reviewing/deleting a worktree, to help the user
decide whether to clean vs. fully remove it (not directly traced to a
specific settings screen, but the shape of the data — total vs. reclaimable
— strongly implies that use).

## Directory selector

`packages/ui/src/react/components/directory-selector/directory-selector.tsx`
— a Finder/Explorer-style column browser (not a native OS picker) used
where the app needs the user to **navigate and pick a folder from inside its
own UI** (e.g. picking a project's location, or a save target) rather than
via `dialog.showOpenDialog`.

### What the user can do
- **Navigate**: back/forward buttons (browser-history style,
  `canGoBack`/`canGoForward` passed in), double-click a folder row to enter
  it, click a breadcrumb segment to jump to an ancestor (breadcrumbs
  computed from the path, `navigationRoot` optionally limits which
  ancestors are clickable — segments above the nav root render as plain
  text).
- **Filter** the current folder's listing with a live text search box
  (client-side substring filter, case-insensitive).
- **Select**: click a directory or git-repository row to select it (click
  again to deselect); files and symlinks are shown but **not selectable**
  (`isSelectableEntry`). Enter key on a focused row navigates into it.
- **Create a new folder** inline (draft row with input, Enter commits,
  Escape/blur-empty cancels) — optional (`onCreateFolder`).
- **Confirm/Cancel** footer buttons — optional; Confirm is disabled until
  something is selected.
- Columns shown: Name, **Size** (human-formatted, `formatBytes` — B/KB/MB/
  GB/TB, whole numbers above 10 units or for bytes, one decimal otherwise),
  **Kind** (Folder / Git repository / File / Symlink), **Date Added**
  (locale medium date format).
- Row icons distinguish plain folders from **git repositories**
  (`FolderGit2Icon`) specifically — i.e. the backing data already knows
  which folders are git checkouts, presumably to steer users toward valid
  project roots.
- Handles **Windows UNC paths and drive letters** as well as POSIX paths in
  its own path-splitting logic (`splitDirectorySelectorPath`), including
  case-insensitive path comparison on the `\\` separator.

### States
`loading` (spinner + "Loading folder"), `error` (message shown inline),
`ready` with `entries.length === 0` → "Empty folder", or "No matches" when
a filter yields nothing (distinguished from a genuinely empty folder).

## Security: workspace path containment

Not a visible "feature" but load-bearing for every file operation above —
worth cataloguing because it constrains what any rebuild must preserve.

- **`realpath-containment.ts`**: `isRealPathContained(files, root, candidate)`
  resolves **both** the root and the candidate through the filesystem's real
  path (following symlinks) before checking containment — so a symlink
  inside the workspace that points outside it is caught. For a candidate
  path that doesn't exist yet (e.g. "create this new file at this path"),
  `realPathNearestExisting` walks up the candidate's ancestors until it
  finds one that does exist, resolves *that*, and re-appends the
  not-yet-created tail segments — so containment can still be validated
  before creation.
- **`workspace-file-policy.ts`**: `assertWorkspaceWriteAllowed` /
  `assertWorkspaceDirectoryTargetAllowed` are the gates every write-shaped
  operation (create, rename, move, delete, directory create) must pass
  through; on failure they return a typed `invalid-path` / path-escape
  `FsError` (e.g. `"Path resolves outside the workspace"`) rather than
  performing the operation. Uses a POSIX-vs-Windows-aware path-semantics
  helper (`createPathSemantics`) so containment checks are correct on both
  path styles.

## Primitives inventory (infra, not directly user-facing)

Included in the requested scan area but are backend plumbing rather than
features with their own UI — cataloged briefly for completeness:

- **`packages/core/src/primitives/path`** — the shared, strongly-typed path
  vocabulary (`HostAbsolutePath`, `PortableRelativePath`, `ResourceUri`,
  `ResourceKey`) used everywhere above to avoid raw-string path bugs across
  the local/POSIX/Windows/SSH-remote boundary; includes parsing, joining,
  containment (`createPathSemantics`), and URI encode/decode for the
  `ResourceUri` wire format keys.
- **`packages/core/src/primitives/plugin-fs`** — a minimal 5-method
  (`read/write/delete/exists/list`) filesystem capability interface, scoped
  for agent **plugins** (not the main app's file features) to read/write
  their own config/state files without a direct `fs` dependency.
- **`packages/core/src/primitives/kv`** — a small key/value store primitive
  (not deeply read; app-settings and similar small persisted values likely
  ride on this).
- **`packages/core/src/primitives/sqlite-store`** — the shared SQLite
  wrapper (Drizzle-based) that both the main app DB and the separate
  file-search DB (see *Search* above) are built on: driver abstraction,
  migration codegen, backup, fingerprinting, and a conformance/invariants
  test harness.
- **`packages/core/src/primitives/versioned-schema`** — a small schema
  versioning/migration helper (not deeply read).

None of these have their own screens; they're the substrate the features
above are built on.
