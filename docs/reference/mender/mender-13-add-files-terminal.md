# Files, terminals and the browser: what to add

Mender already has a working file tree, file read/edit/rename/delete, quick-open and full-text search, and one persistent tmux shell per checkout — all laid over the yard, in MENDER.md's own vocabulary. What's actually missing spans from foundational (no in-app browser, no real full-screen terminal, no way to run an agent's own CLI in a real terminal) to convenience (reopening the last board you closed, opening a file in your own editor). Below is a grain-by-grain pass against Emdash's and cmux's much larger surfaces, re-checked against Mender's source a second time after the first pass cut too fast.

## NEED

### Running an agent CLI in a real terminal, as its own kind of session (TUI conversations) · L
Has it: Emdash (a second, non-ACP conversation type: the actual agent CLI — e.g. Claude Code itself — runs inside a real embedded PTY terminal, not a structured chat transcript; it gets find-in-terminal, a context bar, and its own attention/status classification). Mender: **no** — confirmed by source. `runtimes.ts` starts the `tui-agents` worker (`tuiAgentsWorkerSpec`, required as a `workspace-registry` dependency), but nothing in `apps/mender/src/main/kit.ts`/`agents.ts` or the renderer ever drives it; `mender-04-underneath.md` independently flags it "possibly-vestigial for Mender's UI." Every session in Mender runs over ACP only.
Why it matters most: this is the *only* place Claude Code's own usage-limit and session-limit handling lives — its native red "You've hit your session limit · resets 5pm" banner and "continuing automatically at 5pm" behavior are drawn by Claude Code's own terminal UI, not sent over any protocol. Mender's own read-first catalogue says so explicitly: talking to Claude over ACP instead means a limit "arrives as an ordinary answer on the board, in plain prose, with no reset time pulled out, no countdown and nothing that carries on by itself." Right now Mender has no way to get that back — a session that hits its limit just silently stops helping, in a way the user has no vocabulary for on the board. This is a real functional hole, not a nice-to-have.
Back end: **ready** — the worker is already started, already a workspace-registry dependency, and Emdash's whole TUI-conversation runtime under `packages/core/src/runtimes/tui-agents/` and `packages/core/src/runtimes/terminals/` is inherited whole; Mender just never wires a UI to it.
In the village: not a second board type bolted beside the chat one — a *different way to hang the lantern*. When starting a session (or from the `/agent` card's "who works here"), offer a session shape alongside the agent choice: talk to it structured (what exists today) or sit it down at a real terminal and watch it work (the raw CLI). A TUI-shaped session's yard shows the same fire/gatepost/cart frame, but the middle — where the transcript would render — is the real terminal grid (see the next entry) instead of parsed turns; what you type on the write line at the bottom is handed to the terminal the same way a shell line is, not parsed as a chat message. This is the one place a genuinely different board layout is warranted, because the thing on the other end (Claude Code's own TUI) is drawing its own screen, not speaking a protocol Mender can re-lay.

### A shell that full-screen programs are actually usable in, not just legible · M
Has it: Emdash (xterm.js, full keyboard-addressable cursor anywhere on screen — vim, htop, `less`, any agent's own TUI all work normally). cmux (libghostty, the same). Mender: **partly** — `Screen` (`board/screen.ts`) is a from-scratch VT100-ish grid emulator that correctly *draws* cursor-addressed output (colors/mouse-reporting parsed-and-ignored, but cursor motion, scrolling regions, alternate-screen and insert/delete are all real), but there is no way to *move the keyboard's own input focus* to a cell mid-screen — input always goes to the one line at the foot of the board. `mender-03-board.md` confirms this structurally: "there's no notion of sending input to a specific cell/cursor position beyond the one line at the foot of the board." A full-screen program draws correctly and is unusable.
Why it matters: this blocks two things at once — (1) ordinary shell use (`vim`, `htop`, `less -R`, `git log` in a pager, `tig`) inside the one real terminal the app already has, and (2) it's a hard prerequisite for the TUI-agent-conversation item above, since Claude Code's own terminal UI is itself a full-screen program that needs real keyboard addressing to be driven (arrow keys to navigate a permission prompt, etc.), not just to be watched.
Back end: **ready in substance, needs real wiring** — Emdash's terminals runtime and xterm.js's whole input model already exist and are inherited; this is Mender's own `Screen`/`talking.ts` needing to route keystrokes by cursor position instead of only appending to a foot-of-board input buffer, or (more realistically, given the effort) swapping the hand-rolled `Screen` for the same xterm.js instance Emdash already uses. Either way it's real engineering, not a missing runtime call.
In the village: no chrome change needed — the shell board already looks like a terminal; what changes is that while it's focused, keys go straight to the grid at the cursor's own position (the same way any real terminal app works), with the one line at the foot reserved for when you're *not* inside a full-screen program, the same distinction every terminal app already makes between "line mode" and "raw mode." Given the effort, this is worth doing once, shared by the plain shell and the new TUI-agent session kind above.

### Dev/preview-server detection, surfaced on the checkout board, the yard, and the rail · M
Has it: Emdash (a preview-server pill in the task toolbar: detects local and SSH-forwarded servers, status, "Open in Emdash Browser" / "Open in System Browser" / "Copy URL" / "Restart Forward" / "Stop"). Mender: **no** — grepped for `preview-server`/`devServer`/`dev-server` in `apps/mender/src`, nothing; the `preview-servers` worker is not among Mender's 15 started runtimes.
Why it matters: without detection a user has to already know which port a session's `npm run dev` picked; this is the actual point of the browser pane below — detection is what turns "open a page" into something ever pressed. The coordinator specifically asked this be visible beyond the checkout board too: a session with something live on it is a fact worth carrying onto the rail (where sessions are already distinguished by mood/light) and the yard (where the fire/cart already carry session status), not just buried in a checkout's own offer list.
Back end: **ready** — Emdash's `preview-server-service.ts` and its terminal-output-sniffing detection are inherited whole; this is purely "start the worker and surface it," same shape as every other runtime Mender already wires in `runtimes.ts`.
In the village: a line on the session's checkout board (`→ what's running on :<port>`) opens the browser board at that URL — one line per detected server, most-recent first, same style as `+ send this branch up`. On the rail, a lantern for a session with something live gets a small second mark alongside its mood — not a new color (gold/mood marks are already spoken for), a plain glyph in the margin the way a tool-in-trouble gets `✗` on the `/agent` card, so "something's running here" reads at a glance without opening the session. On the yard itself, the same fact appears as one more line in the cart's list of what the agent did, since starting a dev server is exactly the kind of thing that list already narrates ("set something running" already has a described prop — "a tub over the fire" — in MENDER.md's own cart vocabulary; a detected server is the natural trigger for it).

### An in-app browser pane · L
Has it: Emdash (full `<webview>` pane: URL bar, error pages, dev-server start page, DevTools, profiles, zoom). cmux (a whole embedded WebKit/Chromium browser). Mender: **no** — no `<webview>` tag, no browser pane type, no URL bar anywhere; "browser" only appears in Mender's source as prose comments and OS-external-open calls.
Why it matters: an agent session routinely needs to be shown a running dev server or a page under test, and right now the only route is leaving the app entirely, which breaks "everything is laid over the yard." Paired with detection above, this is the single largest capability gap in this area.
Back end: **needs work** — `webviewTag` is off by default and nothing in `runtimes.ts` starts anything like it; needs `webviewTag: true` plus new main-process partition/profile wiring (Emdash's own browser pane is renderer-side webview + a thin main-process manager, not a `runtimes.ts` worker, so it's new code, not a missing call).
In the village: a board, not a pane or a tab. Pressed from a detected server (above) or a `→ open a page` offer, it lays a browser board over the yard the way a file or the shell does: an address line at the top (typed like the write line), the page below, `back`/`forward` as faded prose lines rather than icon buttons. Escape closes it, same ladder as everything else. First cut deliberately thin — no profiles, no multiple engines, just "show me the page next to my session" and an address line; DevTools, design mode, and the automation API are handled separately below.

### Viewing a file that is a picture · S
Has it: Emdash (image files render inline, click-to-expand; SVG gets its own preview). cmux ("Cmd-clicking readable files opens... images... in cmux"). Mender: **no** — confirmed in `board/reading.ts`: every image extension falls into the same `binary` branch as a compiled `.so` or a `.zip`, rendered as the single line "`<size>` of something that is not writing, so there is nothing to read here." A PNG next to a component and a stripped binary read identically.
Why it matters: this is a real, felt gap the moment someone walks a folder that has any images in it at all (icons, screenshots, design assets, a project's own picture) — which is common, and MENDER.md itself cares enough about pictures to give project icons their own whole flow. A file board that can't show the one file type it's most likely to be asked to show is a real hole, not a nicety.
Back end: **ready** — Mender's own `pictures.ts` already loads and thumbnails images (used for project icons) via `nativeImage`; this is wiring the same capability onto the file-reading path instead of writing new decode logic.
In the village: a picture file's board shows the image itself in place of the line-by-line text — sized to the board's own width, same "read, don't scroll past a size" rule the text view already follows for oversized files. No separate viewer chrome; pressing it does nothing new (there's nothing to edit), and blame/rename/delete still work the same as any other file, since those aren't about the content.

### Live-updating a file you're reading while the agent writes it · S
Has it: Emdash (the editor's `OpenFileStore` keeps a live facet subscription; a save collides with an outside change via a "File Modified Externally" dialog, not silence). Mender: **partly** — the code comment on `openFile()` in `main.ts` explicitly says "Opening one file of it, live, so an agent writing to it shows," but the implementation is a one-shot `client.files.content.state(...).snapshot()`, not a subscription: it refreshes only after *your own* write (`wroteLine`), never in response to the agent changing the file out from under you while you're looking at it.
Why it matters: this is squarely inside the app's own stated design intent (the comment says it should already work), and it's exactly the situation this app is built around — reading a file while an agent is actively working in the same checkout. Right now the board silently goes stale; closing and reopening the file is the only way to see the agent's own change, with no signal that it happened.
Back end: **ready** — `content.state(...)` already returns a live model (used elsewhere, e.g. the checkout board's `head`/`status` subscriptions); this is subscribing to it here instead of taking one snapshot.
In the village: no new chrome — the file board already rewrites itself live the way the checkout board does when a commit lands; wiring the same subscription in means a file you're reading updates under you exactly the way MENDER.md already describes for everything else ("nothing teleports... anything that is the same thing a moment later slides to where it is now"). Worth pairing with a small "changed while you were reading it" notice if the read line/scroll position would otherwise jump, though even a silent live update is strictly better than today's silent staleness.

## WANT

### Rendered markdown (and Mermaid) when reading a file, not just in a transcript · M
Has it: Emdash (Markdown/HTML/CSV/SVG all get a rendered "Preview" mode with a Raw/Preview toggle when opened as a file). cmux (a dedicated markdown viewer/editor with Preview/TextEdit toggle, remote-image consent gating). Mender: **partly** — `board/writing.ts` already renders headings/lists/quotes/rules/tables/code/emphasis-stripping for the agent's own transcript, matching MENDER.md's "agents write in markdown... read rather than shown" almost exactly, but that renderer is never applied to a `.md` file opened through `board/reading.ts` — a markdown file in the folder walker shows as raw text, line-numbered and pressable-per-line like any other file. Mermaid renders nowhere in Mender at all (confirmed: no Mermaid parsing/library reference anywhere in `apps/mender/src`), matching this catalogue's sibling agent-area finding (`gap-01-agents.md`) that the same gap exists in the chat transcript.
Why it matters: a `.md` file read through the folder is a real, common case (READMEs, docs, this very MENDER.md), and today it's shown exactly as unreadable-as-prose as a `.ts` file — worse than what the transcript already does for the same markdown. This is real usability, not cosmetic — a raw `#` and `**bold**` litter a document that would otherwise read clean.
Back end: ready — `writing.ts`'s renderer is pure client-side parsing, already proven on the transcript; reusing it here is wiring, not new logic. Mermaid needs a rendering library added (none exists yet anywhere in Mender), same effort whether it lands here or on the transcript first.
In the village: a `.md` file opened through the folder renders the same way an agent's own words do — the file board becomes prose instead of numbered lines, and line-editing (pressing a line to rewrite it) simply doesn't apply to a rendered paragraph, the same way it already doesn't apply while reading blame. A raw-text toggle isn't needed given this app's stance that reading, not selecting-and-retyping, is the normal mode — editing a markdown file, if ever wanted, would go through the same "press to look for names / press to look inside them" kind of mode-flip already used elsewhere on this board, not a Raw/Preview button (this app has none). A fenced ` ```mermaid ` block inside that rendered file, or inside a transcript, becomes an inline diagram sized to the board's width, pressable to open larger over the yard the same a picture would be — no dedicated viewer chrome needed given the board already has a read-scrim.

### Quick-open and full-text search reachable directly from the yard, not only after walking into the folder · S
Has it: Emdash (`@files` from the command palette, reachable from anywhere). cmux (a `Global Search` overlay across the whole app, plus a per-pane Cmd+P). Mender: **partly** — `named()`/`written()` (quick file-name search and full-text content search) both exist and work well (`finding.ts`, exposed on the board as `looking.ts`), but the only door into them is `→ look for something in here`, offered on the folder board — which means you must already have pressed `→ inside` to walk the checkout before you can search it. There's no way to jump straight from a session's yard to "find a file by name" the way `Cmd/Ctrl+K` already jumps straight to a session or project.
Why it matters: a real but modest friction — the underlying search is already good, it's one avoidable extra press away from where a user actually is (the yard) every single time.
Back end: ready — `named`/`written` are already wired and working; this is a new entry point onto the same calls.
In the village: fold it into the existing `Cmd/Ctrl+K` finder rather than inventing a second overlay (this app already has exactly one "board with everything on it, narrowing as you type" surface, and MENDER.md's own design bias is against a second one). While standing in a session or district, typing past what matches sessions/projects/doings could fall through to a file-name match in that checkout — the finder's own layout already reserves a spot for "held with command" as a trailing, lower-priority section; a trailing "in this checkout" section for file matches would follow the same pattern, opening the file directly on Return the way a session does today.

### Opening a file or folder in the user's own external editor / Finder · S
Has it: Emdash (a whole directory of ~30 detected external editors, an "Open in" menu per file). cmux ("Cmd-clicking readable files... Reveal in Finder," a configurable preferred-editor fallback). Mender: **partly** — `window.mender.openIt`/`showIt` (wrapping `shell.openPath`/`shell.showItemInFolder`) already exist and are wired for a project's own settings window (`show: () => window.mender.showIt(project.path)`) and the pull-request board's "open externally" offer, but there is no equivalent offer anywhere on the file-reading or folder-walking board itself — you can reveal a *project's* root in Finder, but not a specific file you're looking at.
Why it matters: nice, not blocking — most file work in this app is meant to route through the agent, and the line editor covers small human fixes. But there's a real, common case this app doesn't serve well: a change big enough to want a real editor for, or a binary/unsupported file type Mender can't render at all (a design file, a font, a video) where "open in default app" is the only sane offer, and today there isn't one.
Back end: ready — the exact same preload bridge already used elsewhere (`openIt`/`showIt`) covers this; no new capability needed, no external-editor-directory work required (unlike Emdash's named-editor-per-app approach) since "open in default app" already does the job for the binary/too-large cases specifically.
In the village: a file board that can't render its own content (binary, too-large) already shows a faded status line explaining why; add a `→ open it properly` offer right there, using the file's own path with the existing `openIt()` bridge — exactly the same shape as the folder's own "Show in Finder" line already works at the project level, just reachable one level deeper, at a specific file.

### Pasting or dropping images and files into the shell · S
Has it: Emdash (dropped/pasted files become bracketed-paste file-path input the CLI can read; images get re-persisted past Chromium's temp-file deletion window; drop caps at 50MB). Mender: **no** — `talking.ts`/`shell.ts` have no drop/paste handling beyond whatever xterm-equivalent... actually Mender's own hand-rolled `Screen` has none at all; the only place Mender currently accepts a dropped picture is the agent's own write line (per MENDER.md: "Drop or paste one on a session's board and it waits by the line... goes with what you say").
Why it matters: modest — most of what a dropped file is for in this app already has a home (the agent's write line). But once the shell becomes a real, full-screen-capable terminal (see NEED above) and hosts real CLI tools directly, a user working at that shell — not talking to the agent — has no way to hand it a file path by dropping one, the way they already can with the agent.
Back end: ready — Emdash's path-escaping/bracketed-paste injection logic (`terminal-image-paths.ts`/`terminal-image-injection.ts`) is portable, no runtime dependency; Mender's shell already knows how to send text to the PTY (`shell.say()`).
In the village: dropping a file onto the shell board writes its path onto the shell's own input, the same mechanical shape as dropping onto the write line does today (per MENDER.md, "it waits... then goes with what you say") — except a shell has no separate "say" step, so it lands as typed text ready to send rather than an attachment held until Return. Worth doing only after (or alongside) the full-screen-terminal work, not before.

### The browser's element-picker / "design mode," handing a selected element to the agent · L
Has it: cmux only (a rich element-inspector: click or freehand-draw a region, captures a screenshot plus DOM/CSS/React-prop metadata, composes it with typed notes into a clipboard handoff for an agent). Mender: **no** — no browser exists yet at all (see NEED above), so this is necessarily downstream of it.
Why it matters: genuinely cool and genuinely useful once there's a page on screen at all — "point at this button, say what's wrong with it" is exactly the kind of thing an agent session benefits from, and it's a natural extension of the browser board once it exists, not a separate feature bolted on. Reconsidered up from a flat cut: this deserves a real village-shaped design, just scoped far smaller than cmux's (no React-prop inspection, no freehand-draw mode, no composer popover with per-element chips).
Back end: needs work, but incrementally — once the plain browser pane above exists, this needs page-side click-to-select JS (portable, no runtime dependency) plus a screenshot capture call (Electron's own `webContents.capturePage` covers the mechanics cmux does with more machinery).
In the village: a `→ point at something` line on the browser board turns the cursor into a picker; clicking an element outlines it and writes one line on the browser board describing what's selected (tag, a short snippet), with a `→ hand it to the session` offer right there — pressing it drops a picture (the element's own screenshot) onto the write line exactly the way any other picture drop does today, with the element's markup/selector as the accompanying text. No separate composer popover, no chips, no multi-element selection for a first cut — one element, one handoff, using the mechanism this app already has for pictures.

### Screenshots of a page handed to the agent · S
Has it: Emdash ("Copy screenshot" toolbar button, copies to OS clipboard). cmux (whole-page and drag-selected-region screenshot, with a camera-flash animation, direct clipboard copy). Mender: **no** — downstream of the browser pane existing at all.
Why it matters: smaller and more general than the design-mode item above — sometimes you just want the agent to see the whole page, not point at one element. Cheap once the browser exists.
Back end: ready once the browser pane lands — `webContents.capturePage()` is a single Electron call.
In the village: a `→ hand this page over` line on the browser board, pressed once — drops the current page as a picture onto the write line, same mechanism as every other picture-to-agent handoff in this app. No selection UI, no flash animation (this app settles rows back gold-then-plain instead of a camera-flash cue); the offer itself is the whole interaction.

### Reopening the last board you closed · S
Has it: Emdash (Reopen Closed Tab). cmux (a shared closed-item history across panels/workspaces/windows, plus "Restore Previous Launch" for a whole session). Mender: **no** — Mender has back/forward stepping through where you've been (`Cmd/Ctrl+[`/`]`, the finder's own chord table), but nothing that remembers a board you actively *closed* (Escaped all the way out of) so it can be reopened deliberately.
Why it matters: modest — Mender's back/forward already covers most of what this would be for (undoing an accidental Escape), but it doesn't cover the case of closing something on purpose and then wanting it again a minute later, which back/forward can walk past rather than land on cleanly.
Back end: ready — this is pure renderer-side history bookkeeping on top of state Mender already has (what board was open, for what place).
In the village: fold into the same `Cmd/Ctrl+[` back-stepping the app already has, rather than a new chord — closing a board (Escape at the top of its own ladder) is already indistinguishable from any other backward step in principle; the only change needed is remembering it as a landable stop rather than a transient one so stepping back reliably lands you where you were, not past it.

## SKIP

### Canvas/freeform pane layout, splits, multiple panes per workspace · genuinely against the design
Has it: cmux only (a whole Bonsplit split-tree engine plus a separate freeform 2D canvas mode). Reason to cut, not just defer: MENDER.md states the rule this would break in so many words — "not several boards, not propped panels, not split panes." This isn't an under-designed feature waiting for a village form; multiple simultaneous boards is the one thing this whole app is built to not be. A village-shaped version of "more than one thing visible at once" doesn't exist because the app's premise is that it shouldn't.

### Full Ghostty-style terminal font/theme/config customization · genuinely against the design
Has it: cmux only (deep config-file-driven fonts, 16-color palettes, background blur, per-directive theming). Reason to cut: MENDER.md is explicit that the whole app draws in one typeface (Departure Mono) with no size/weight system beyond what the board rules already define — this is stated as a deliberate constraint on the *whole app*, not just the shell, so a terminal-only font/theme picker would be a real, single exception to a rule that's otherwise universal. (If accessibility ever demands adjustable text size app-wide, that's a different, whole-app request — not a terminal-scoped one.)

### Simulators (iOS/Android device panes) · genuinely out of scope
Has it: cmux implies this in name only in this pass — not independently confirmed as a distinct cmux feature (flagged unverified in the original pass, worth re-checking against cmux's own catalogue directly if this becomes live). Reason to cut regardless: a village of git worktrees and agent sessions has no natural relationship to a device simulator, and this repo carries a standing platform rule against installing iOS tooling at all. Not a design gap — genuinely a different kind of app.

### Full browser automation API (125 CLI-driven actions, CDP/Playwright-style) · genuinely redundant here
Has it: cmux only — an entire scriptable protocol (`cmux browser click/type/eval/...`) meant for *external* tooling to drive cmux's browser. Reason to cut: Mender's agent already has real file/shell/git tools through ACP; a second, parallel automation surface aimed specifically at a browser pane duplicates capability the agent already has by other means (it can already read files, run commands, and — once the browser pane and element-picker above exist — see and point at pages). This is infrastructure for cmux's different use case (an external CLI/other programs driving the browser), not a gap in what Mender's own agent sessions can do.

### Cookie/history import from other installed browsers, multiple rendering engines, browser profiles · genuinely a different product's scope
Has it: cmux only, in real depth (22 supported source browsers, 3 destination modes, WebKit-vs-Chromium engine choice). Reason to cut: this is infrastructure for a browser meant to be someone's daily driver, with its own history and signed-in sessions across many sites. Mender's browser board (see NEED above) is scoped to "show one page next to one session" — it doesn't accumulate its own history or identity worth importing into. If the browser pane above ever grows real day-to-day use, this would be worth revisiting, but it isn't a village-shaped version of a Mender need today, it's a feature for a different kind of tool.

### Saved terminal/workspace layout templates · depends on a cut feature
Has it: cmux only. Reason to cut: this only means anything once there are multiple panes/splits to save a layout *of*, which is cut above for design reasons, not oversight. No independent reason to build this once its prerequisite is gone.

## Already have
- Persistent, tmux-backed shell per checkout, surviving app restarts (`talking.ts`) — matches cmux's/Emdash's terminal persistence.
- Full-screen TUI *rendering* in the shell (correct cursor-addressed writes) — the output half of the full-screen-terminal gap above is already solid; it's input addressing that's missing.
- Quick file-name search and full-text content search (`finding.ts`, `looking.ts`) — equivalent in kind to Emdash's `@files` quick-open and file-content search, minus a direct-from-anywhere entry point (see WANT above).
- File tree walk/read/rename/delete/create, with blame ("who last touched it") — equivalent in kind to Emdash's file-tree sidebar minus multi-select/cut-copy-paste/drag-drop.
- One-line-at-a-time file editing with an etag "changed underneath you" guard — a deliberate, narrower alternative to Emdash's full Monaco editor, not a gap (see `gap`-adjacent note: the one real problem here is the already-catalogued invisible-cursor rendering bug, a fix rather than a missing capability).
- Markdown rendering of *agent output* on the board (headings, lists, quotes, rules, tables, code blocks — press-to-copy) — matches Emdash's markdown renderer's substance; extending it to file-reading is the WANT item above.
- Diff reading (changed files, undo/revert, commit diffs) via a hand-rolled Myers diff — functionally equivalent to Emdash's diff viewer for reading; no in-place diff editing, consistent with the one-line-editor design choice.
- Git checkout board: status, commit, push/pull/publish, PR board with checks/merge/ready-for-review — covers the git-adjacent half of Emdash's terminal/editor/files slice; not itself in this area's remit but load-bearing context for why several items above are lower priority than they'd otherwise be.
- Large-file and unreadable-file handling (a size-capped text view, a distinct "too large" message, a distinct binary message) — matches Emdash's file-tab placeholder states in substance; the one real remaining hole in this family is picture rendering specifically (NEED above), not large/binary handling generally.
